# v0.8 — Memory Safety + Avalonia Redesign & Repositioning

**Date:** 2026-07-26
**Status:** Approved — proceed to implementation plan
**Baseline:** v0.7.0, `main` clean, 408/408 tests passing

---

## 1. Context

Crustcut is a Windows performance optimizer built in C# / .NET 9 / WPF, currently ~24k
lines across four projects (`Core`, `Win`, `UI`, `Tests`).

Two user-reported problems and one strategic shift drive this release:

1. **The memory optimizer degrades apps in active use** — most visibly VS Code, which
   stalls, types laggily, and hangs its extension host after a cleanup runs.
2. **The UI looks dated** and lacks visual hierarchy.
3. **The product is repositioning** from "gaming software" to general-purpose
   performance software, with a cross-platform (Windows + macOS) future.

### Scope decomposition

The full request spans four independent projects. Only the first two are in scope here;
the remaining two are deferred and will each get their own spec → plan → implementation
cycle.

| # | Project | Status |
| --- | --- | --- |
| 1 | Memory safety + stability | **In scope (this spec)** |
| 2 | Avalonia redesign + repositioning | **In scope (this spec)** |
| 3 | `Core` platform split (`Core` / `Core.Windows`) | Deferred |
| 4 | macOS capability layer + Mac build | Deferred |

Projects 1 and 2 are independent of each other and touch disjoint files. They may be
built and reviewed as separate workstreams within one release.

## 2. Workstream A — Memory optimizer safety

### 2.1 Problem

Two entry points reach the same destructive code path:

- **Manual:** `RamCleanerTweak.ApplyAsync` (`Core/Tweaks/RamCleanerTweak.cs`) calls
  `IProcessClient.TrimAllUserProcesses()`.
- **Automatic:** `PriorityRuleEngine.OnProcessStarted` → `GameBooster.QueueAsync` →
  `SafeRamCleaner.RunAsync`, firing two seconds after a game launches and trimming
  every process whose working set exceeds 100 MB.

Both ultimately call `EmptyWorkingSet` (`Core/Memory/WorkingSetTrimmer.cs`), which evicts
a process's entire working set to the pagefile. Every page the process next touches is a
hard fault from disk.

VS Code is an Electron application: the main process, each renderer, the extension host,
and every language server comfortably exceed the 100 MB threshold. The existing
`SafeRamCleaner.SystemProcessNames` guard list covers only OS infrastructure
(`csrss`, `lsass`, `explorer`, …) — nothing protects user applications unless the user has
manually created a Memory Priority rule.

The path then calls `FlushFileCache()` and `EmptyStandbyList()`, which purge the
**machine-wide** file cache and standby list. This evicts cached pages belonging to every
process on the system, so the pages a trimmed application needs are not merely out of its
working set — they are out of RAM entirely and must be re-read from storage. The net
effect is a system that is measurably slower after a "cleanup" than before it.

The tile's user-facing description currently asserts this is "safe."

### 2.2 Design

**Protection is derived from structure, not from a hardcoded application list.**

A process is protected from trimming if **any** of the following hold:

1. It owns a visible top-level window.
2. It is the foreground process.
3. It shares an executable name with any process satisfying (1) or (2).
4. It is a descendant, at any depth, of a protected process.
5. It appears in the user's Memory Priority protect list (`ProtectFromRamCleanup`).
6. It is a known system or shell process (the existing `SystemProcessNames` set).
7. It is Crustcut itself.

**Rule 4 is what actually fixes the reported bug.** `Code.exe` owns a window and would be
caught by rule 1, but its renderers, extension host, and language servers do not own
windows and would still be trimmed under a window-only rule — and those are precisely the
processes whose stalls surface as laggy typing and unresponsive extensions. Protecting the
full process tree is required for the fix to be real rather than cosmetic.

Any process not protected is trimmed only if its working set meets or exceeds the
threshold (unchanged at 100 MB).

**Removals.** `EmptyStandbyList()` and `FlushFileCache()` are deleted from both call sites
and from `IWorkingSetTrimmer`. They cannot be made safe: their blast radius is the whole
machine by definition, and neither has a defensible benefit on a system with adequate RAM.

**Retained behaviour.** Automatic trimming before a game launch is kept — it has real
value — but runs under the protection rules above, so an open editor or browser is no
longer collateral damage.

**Honest copy.** `RamCleanerTweak.Description` stops claiming the operation is safe and
states plainly what it does and what it costs.

### 2.3 Structure

The Core/Win separation is preserved. `SafeRamCleaner` remains **pure logic**: it receives
process snapshots and computes the protected set, with no interop, and is therefore fully
unit-testable against fabricated process trees.

- **`Win`** gains process-tree and window enumeration:
  - `CreateToolhelp32Snapshot` / `PROCESSENTRY32.th32ParentProcessID` for parent PIDs.
  - `EnumWindows` + `IsWindowVisible` + `GetWindowThreadProcessId` for windowed PIDs.
  - `GetForegroundWindow` for the focused process.
- **`ProcessSnapshot`** gains `ParentPid` and `HasVisibleWindow`.
- **`SafeRamCleaner`** gains protected-set computation, including transitive descendant
  expansion.

### 2.4 Tests (written first)

- **VS Code scenario:** `Code.exe` owning a window plus five windowless children, all
  above threshold → asserts **zero** trims.
- **Foreground protection:** the focused process and its tree are never trimmed.
- **Executable-name protection:** a second instance of a windowed application, itself
  windowless, is protected.
- **Positive case:** a windowless background service above threshold with no protected
  ancestor **is** trimmed — the feature must still do something.
- **Regression:** `EmptyStandbyList` and `FlushFileCache` are never invoked.
- **Cycle safety:** descendant expansion terminates on malformed or cyclic parent data.

### 2.5 Stability investigation

The user reports believing Crustcut itself degrades system performance. This will be
**measured before it is changed**: sustained idle profiling of CPU, private bytes, handle
count, and thread count, followed by targeted fixes driven by the measurements.

Suspects to check first — these are hypotheses, not findings, and none should be "fixed"
without evidence:

- `HardwareClient.SampleGpuPercent` re-enumerates every GPU performance-counter instance
  on every sample.
- `WmiProcessWatcher` uses `Win32_ProcessStartTrace`, a known-expensive WMI event source.
- `GameProcessWatcher` polls on a two-second timer.

## 3. Workstream B — Avalonia redesign & repositioning

### 3.1 Toolkit decision

The redesigned UI is built in **Avalonia**, not WPF. WPF cannot run on macOS; building the
redesign in WPF and porting later would mean paying for the redesign twice. Avalonia's
XAML is close enough to WPF's that porting views is largely mechanical, and the
genuinely platform-specific pieces are few and well contained.

### 3.2 Migration strategy — the working app is never broken

`PrimeOSTuner.UI` (WPF) is **frozen and left untouched**. The Avalonia application is built
alongside it in the same solution. WPF and its associated tests are deleted in a single
final commit once the new app reaches parity.

This trades some temporary view-model duplication for two guarantees: a runnable
application at every commit, and `Core`/`Win` remaining untouched so the 408-test suite
stays green throughout.

### 3.3 New projects

- **`Crustcut.Presentation`** — view-models only, no UI framework dependency. References
  `Core`; uses `CommunityToolkit.Mvvm` (already cross-platform).
- **`Crustcut.App`** — the Avalonia application. Targets `net9.0-windows` initially;
  becomes `net9.0` when project 3 splits `Core`.

**`IUiDispatcher`.** Six view-models (`DashboardViewModel`, `GameBoostViewModel`,
`GameLibraryViewModel`, `OverlayViewModel`, `SentinelViewModel`, `SettingsViewModel`)
currently call `System.Windows.Application.Current.Dispatcher` directly. These are replaced
with an injected abstraction:

```csharp
public interface IUiDispatcher { void Post(Action action); }
```

Avalonia implements it via `Dispatcher.UIThread.Post`; tests implement it inline. Besides
removing the WPF coupling, this makes those six view-models properly unit-testable for the
first time.

### 3.4 Platform services requiring reimplementation

| Today (WPF) | Avalonia replacement |
| --- | --- |
| `H.NotifyIcon.Wpf` tray icon | Avalonia built-in `TrayIcon` (cross-platform) |
| `WindowChrome` custom caption | `ExtendClientAreaToDecorationsHint` |
| Click-through overlay | Avalonia window + `SetWindowLong` interop behind `IOverlayPlatform` |
| `RegisterHotKey` message hook | Same interop behind `IGlobalHotkey` |
| `MarkdownView`, sparklines, boost ring | Ported — `Path`/`PathGeometry` are near-identical |
| `WPF-UI` package | Removed; replaced by the token-driven design system |

**The click-through overlay is spiked first**, before the migration is committed to. It is
the one component where Avalonia may genuinely resist, and discovering that early is worth
the time.

### 3.5 Design system

All visual language lives in a single `Theme/Tokens.axaml`. Views reference tokens
exclusively; no literal colours, sizes, or radii in view markup. This is what makes both
future restyling and the macOS port cheap.

Tokens cover: a surface ramp, a text ramp, accent (wheat → crust gradient), status colours
(good / warn / danger), a type scale (44 display / 19 title / 12.5 body / 8 uppercase
label), a 4-8-12-16-24 spacing scale, radii (8 small card / 14 card / 22 pill), and two
shadow definitions (card, glow).

**Approved visual direction** (validated against mockups during brainstorming — "calm and
confident, with real visual weight"):

- Ambient warm radial glow behind the page, so the background is not dead flat.
- Boost score rendered as a gradient arc with **padded geometry bounds** so its glow is
  never clipped into a visible box.
- Live sparklines on every statistic — no bare numbers.
- Game cover art anchoring the session card, with the frametime graph bleeding into it.
- Soft translucent surfaces with shadows; no hard borders.
- Status bar flush to the bottom edge of the navigation rail, full width.
- Shared 56px baseline between the rail's brand row and the page eyebrow.
- A single 12px gutter, with all grids snapping to the same column edges.

Explicitly rejected from the current build: glossy vertical gradients on buttons and cards
(they read as early-2010s Aero), uniformly sized dashboard tiles (nothing leads the eye),
and `#8A5A2C` deep crust against near-black (insufficient contrast).

**Every view is redesigned**, not only the Overview page.

### 3.6 Repositioning

Gaming becomes one section of a performance tool rather than the product's frame.

```
Overview

PERFORMANCE          GAMING              LEARN
  Optimize             Games               Guides
  Diagnosis            Sessions
  Cleanup              Game Boost
  Memory

                              History · Settings (bottom)
```

**Renames:** Dashboard → Overview, Bloatware → Cleanup, Library → Games,
Sentinel → Sessions. *Sentinel* is a good name but conveys nothing to a new user;
*Sessions* describes what the tab shows.

**Copy changes:** "Watching games" → "Watching apps"; the watcher describes monitoring
applications generally; tweak descriptions that assume a gaming context are generalised
where the underlying tweak is not gaming-specific; the README tagline drops "for gamers."

### 3.7 Sequencing

1. Spike the click-through overlay in Avalonia.
2. Create `Crustcut.Presentation`; introduce `IUiDispatcher`; port view-models with tests.
3. Create `Crustcut.App`: window chrome, navigation rail, `Tokens.axaml`, tray icon.
4. Build the Overview page — the flagship of the new design.
5. Port remaining views one at a time, redesigning each.
6. Implement platform services: overlay, global hotkey.
7. Parity check, then delete `PrimeOSTuner.UI` and its four test files in one commit.
8. Validate publish, elevation manifest, and autostart.

### 3.8 Risks

- Avalonia's self-contained single-file publish differs from WPF's and needs validating
  before release.
- The administrator manifest and self-elevation logic must be redone for the new
  executable.
- The autostart scheduled task points at a specific executable path; it must be updated or
  it will silently continue launching the old build.
- Temporary view-model duplication between the frozen WPF project and `Crustcut.Presentation`
  is accepted deliberately; it is resolved by step 7.

## 4. Out of scope

- Splitting `Core` into platform-neutral and Windows-specific assemblies (project 3).
- Any macOS capability implementation or Mac build (project 4).
- New optimization tweaks — the catalog is unchanged this release.

---

## 5. Success criteria

- Trimming memory with VS Code open causes **no** observable degradation to VS Code.
- `EmptyStandbyList` and `FlushFileCache` no longer exist in the codebase.
- The RAM cleaner still measurably reclaims memory from genuinely idle background
  processes.
- Idle resource usage of Crustcut itself is measured, documented, and any regression found
  is fixed.
- The Avalonia application reaches feature parity with the WPF application, which is then
  deleted.
- Every view is redesigned against `Tokens.axaml`, with no literal colours in view markup.
- Navigation and copy present Crustcut as general performance software.
- The test suite passes, having grown to cover the new protection logic and the six
  previously untestable view-models.
